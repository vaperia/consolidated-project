PROJECT 01 · DATABASE / FULL STACK / NLP

Tourism Web Application with NLP

A tourism application that brought together a web interface, backend services, relational and NoSQL databases, and natural-language processing.

JavaScriptNode.jsPython MySQLFirestoreSpaCy

Project goal

The project was designed around building a working tourism information application rather than treating databases as isolated tables. The system needed to store and retrieve information such as users, destinations and reviews while connecting that data to an application that a user could interact with.

What was built

The application used MySQL and Firestore for persistent data, JavaScript and Node.js for application/backend functionality, and Python with SpaCy for NLP-related features. The repository includes the application source, SQL data, backend routes, AI-service code and supporting project documentation.

What happened during development

  • Application workflows had to connect the front end, backend services and database operations rather than being developed independently.
  • Relational MySQL data and Firestore NoSQL data required different ways of structuring and accessing information.
  • The NLP portion introduced an additional Python service into a project that also used JavaScript/Node.js, requiring clear separation between components.
  • Retrieval, updating and presentation of tourism information had to remain consistent across multiple layers of the application.

My engineering contribution

  • Worked on application workflows linking front-end components with backend services and database operations.
  • Used JavaScript, Node.js and Python across different parts of the system.
  • Integrated SpaCy-based NLP functionality into the tourism application.
  • Worked with MySQL and Firestore as two different persistence technologies.

What I learned / gained

  • How a real application is divided into UI, backend, database and AI/NLP components.
  • Why database design affects the rest of an application's architecture.
  • How relational and NoSQL databases solve different data-storage problems.
  • How to integrate services written in different languages into one system.
  • More experience debugging problems that cross component boundaries instead of existing in a single file.

PROJECT 02 · COMPUTER NETWORKS / IOT

Smart Home Network & IoT System

A smart-home communication project used to connect networking theory with how actual connected devices exchange information across wired and wireless networks.

LAN / WLANSwitchingIP Routing Socket ProgrammingIoT Protocols

Project goal

The aim was to understand an IoT system from the network underneath it: how devices join a network, how packets move between networks, how end-to-end communication works, and how application-layer services sit on top of those lower layers.

What was built / modelled

The smart-home design incorporated wired and wireless LAN concepts, switching, IP addressing and routing, transport-layer communication, socket programming and IoT application-layer communication between devices and services.

What happened during development

  • The project required thinking about the system in layers instead of treating “networking” as a single function.
  • Device-to-service communication had to be understood from local connectivity through routing and transport to the application protocol.
  • Socket-programming concepts connected theoretical transport-layer ideas with actual client/service communication.
  • The smart-home context made it necessary to think about how different devices and network segments work together as one system.

Engineering skills demonstrated

  • LAN and WLAN fundamentals.
  • Switching, IP addressing, packet forwarding and routing.
  • Transport-layer and end-to-end communication concepts.
  • Socket and IoT application-layer protocol concepts.

What I learned / gained

  • A stronger end-to-end understanding of how network layers interact.
  • How a problem observed at the application level may actually originate at a lower network layer.
  • How IoT devices depend on ordinary networking fundamentals such as addressing, routing and transport.
  • More confidence reasoning about communications between distributed devices and services.

PROJECT 03 · PROGRAMMING FUNDAMENTALS / API INTEGRATION

AI Chatbot Application

A Python application that combined conversational functionality, a user interface, persistent chat data and external API information.

PythonSQLiteAPIs GUIWeather Data

Project goal

The project was an early exercise in moving beyond small standalone programs and building an application made from multiple modules: chatbot logic, user interface, data persistence, file handling, settings and external data.

What the source contains

The committed source is divided into modules including GUI, chatbot logic, database management, file management, settings and weather handling. A SQLite database is included for chat-log persistence.

What happened during development

  • Chatbot behaviour had to be connected to the surrounding application rather than living as one script.
  • External API responses introduced data that the program did not fully control, requiring handling and integration logic.
  • SQLite was used to persist application data instead of losing state whenever the program stopped.
  • Breaking the system into modules made debugging and responsibilities clearer than putting all functionality into one file.

My contribution

  • Built core chatbot functionality in Python.
  • Integrated external APIs, including weather information.
  • Worked with SQLite queries and data handling.
  • Contributed to debugging, deployment groundwork and additional application features.

What I learned / gained

  • How to decompose a larger Python application into modules with separate responsibilities.
  • How API integration differs from purely local program logic.
  • How persistent storage changes application design.
  • Practical debugging experience across GUI, data and external-service boundaries.
  • A foundation for later backend and full-stack development work.

PROJECT 04 · OPERATING SYSTEMS

OSEK Operating Systems Project

An operating-systems coursework project using an OSEK-based implementation and SimuOSEK project configuration.

OSEKOperating Systems SimulationTask / System Behaviour

Project context

The repository contains the OSEK group-project source, a SimuOSEK project file and the submitted group report. This makes the project useful as evidence of hands-on operating-system coursework rather than only theoretical study.

Development focus

The work required using an operating-system framework and simulator to reason about system behaviour. The implementation therefore involved both program logic and the rules imposed by the execution environment.

Skills demonstrated

  • Working inside an OS/RTOS-style framework rather than a normal single-process program.
  • Reading project configuration together with implementation code.
  • Testing system behaviour using simulation tooling.
  • Documenting design and results in a technical report.

What I learned / gained

  • How execution models and operating-system rules influence application behaviour.
  • Why timing, task interaction and system configuration matter in low-level systems.
  • Experience relating implementation results back to a formal technical report.

PROJECT 06 · EMBEDDED SYSTEMS

Embedded Systems Group Project

A group embedded-systems implementation supported by source code and a formal project report.

Embedded SystemsHardware / Software DebuggingSystem Integration

Project context

The repository contains the Group 10 implementation and its technical report. Unlike purely software-focused coursework, embedded development requires the code to be considered together with the behaviour and constraints of the target system.

Development focus

The project provided experience with an implementation where system behaviour cannot be understood only by reading application logic. Testing, integration and hardware/software interaction become part of the development process.

Skills demonstrated

  • Working with embedded-system source code and project structure.
  • Testing and debugging behaviour in a constrained system context.
  • Connecting implementation work with engineering documentation.
  • Collaborating on a group technical project.

What I learned / gained

  • A stronger appreciation for hardware/software integration.
  • Why embedded debugging often requires observing system behaviour rather than only inspecting code.
  • How constraints at the system level influence implementation decisions.
  • Experience documenting an embedded implementation in a formal report.
